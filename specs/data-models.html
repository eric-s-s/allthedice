Data Models Spec

Separate data models from views in interface.js, so nothing is matched by array position.

Colors are assigned when a dice table first loads, not when its request is created. Only §3 would change if that decision changes.

1. Goals

  1. Every piece of state lives in a plain data model. The DOM is never the source of truth.
  2. Nothing is matched by array position. Dice tables, stats ranges and their colors are linked by id and by stored indexes.
  3. Colors stay with a dice table or range for its lifetime. Removing one doesn't recolor the others.
  4. Every model has a JSDoc type, and tsc --noEmit checks the code in make test and CI.
  5. The Lambda response is checked once, when it arrives (parseDiceTable).

Out of scope: panel minimizing, menus, the Lambda API, SciNum, AliasTableRoller internals, and visual design.

Invariants:

  • colorIndex is non-null if and only if diceTable is set.
  • rollHistory is empty unless diceTable is set.

AppState

{diceTableRequests: DiceTableRequest[], statsRequests: StatsRequest[]}

The order of the arrays is creation order. It decides the order of the plot traces, table columns and roller rows, but not colors.

Debugging access: the state is exposed as window.allTheDice.state, so it can be read from the browser console without a breakpoint. It's a debugging aid, not an API: nothing in the app reads it, and writing to it from the console is unsupported.

Derived values (computed in render(), never stored)

  • loaded = diceTableRequests.filter(r => r.isLoaded)
  • StatsCell = {statsRequest, diceTableRequest, stats}, built for each pair of a submitted range and a loaded table. The plot and stats table read each cell's own references instead of matching two arrays by index.

3. Color assignment

  • colorIndex is assigned in DiceTableRequest.load() on the first successful load, as lowestUnusedIndex(the colorIndex values of the other requests). It stays the same on later reloads and is freed when the request is removed. A failed load assigns nothing.
  • shiftIndex is assigned on a stats request's first submit, using lowestUnusedIndex over the other stats requests. It's freed when the request is removed.
  • Allocation happens in a function that receives AppState (lowestUnusedIndex in models.js). The models only store the result.
  • Index to color stays in plothelpers.js:
    • Swatch, plot line and table header: getTraceColor(colorIndex)
    • Fill: getStatsFillColor(colorIndex, shiftIndex)
  • Single palette: plotlyDefaultRgb is the only list of colors. getTraceColor builds its hex string from it.
function lowestUnusedIndex(usedIndexes) {
    let index = 0;
    while (usedIndexes.includes(index)) {
        index++;
    }
    return index;
}

4. Views

  • DiceTableRequestView: owns its form, input, submit button, error element and swatch.
    • Constructor: (model, actions).
    • Its listeners update the model or call actions (submit, remove). They never write DOM state the model doesn't hold.
    • update(model) sets disabled, aria-busy, the error text and whether it's hidden, and the swatch color. It sets input.value only when it's different from the model, so the cursor isn't reset.
  • StatsRequestView: works the same way. update sets min/max, and fills low.value/high.value from the model when they differ.
  • Plot, stats table and roller rows are rebuilt from the state on every render, as they are now. Roller rows read rollHistory from the model.

5. Connecting views to models

  • onPageLoad keeps the state in an AppState, and keeps two maps: Map<id, DiceTableRequestView> and Map<id, StatsRequestView>.
  • render() goes through each model list in order:
    • It creates and appends a view for any id that doesn't have one, calls view.update(model), and appends the view's element so the DOM order follows the model order.
    • It then removes the views and DOM elements for ids that no longer have a model.
  • Only views write to the DOM, and only during update. Only event handlers, submit and load change the models, and they call render() afterwards.
  • Filling blank stats inputs (today's fillBlankInputsWithLoadedRolls) becomes a step in render() that runs before the views update. It writes the lowest and highest rolls into lowInput/highInput when they're blank, and the views then show those values.

9. Decisions and open questions

Decided

  1. A stats range gets its shift on first submit, not at creation. This matches dice tables getting their color on first load.
  2. buildStringInput is copied on every input event. Copying only on submit would leave the model out of date: an example would treat a request with typed but unsubmitted text as blank and overwrite it, and any render would reset the input to the stale value. The same applies to lowInput/highInput.
  3. The server is not changed. It keeps sending range as [low, high]. Internally the model uses {low, high}, and parseDiceTable converts it.
  4. The work is done in two stages. First, the models, parseDiceTable and type checking, with no behavior change. Second, the views, stable colors and the test rewrites.
  5. A failed reload keeps the old table (unchanged from today). Wiping it would throw away the plot line, stats column, roll history and color on a typo or a network failure.
  6. No loadedBuildString field. Nothing currently needs to know which build string produced the loaded table, so it isn't added. Add it only if a behavior change needs it.
