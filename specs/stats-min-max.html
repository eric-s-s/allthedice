Stats MIN/MAX Spec

Let each end of a stats range follow the lowest or highest roll (MIN / MAX), or be pinned to a number.

Snap rule: a pinned number below the lowest roll becomes MIN, and one above the highest roll becomes MAX. It changes both the box and the submitted range, and it runs on every render.

1. Goals

  1. Each end of a stats range is either MIN, MAX, or a pinned whole number.
  2. New ranges start as MIN to MAX.
  3. MIN always means the lowest roll of the loaded dice tables, and MAX the highest. A submitted range that uses them re-labels and re-shades by itself when tables load or are removed, without being submitted again.
  4. A pinned number stays put until it falls outside the rolls the loaded tables can make. Then it snaps to MIN or MAX.
  5. The user can still step a value by 1, as the number spinner allows today. Pressing − on a box holding the lowest roll changes it to MIN, and pressing + on a box holding the highest roll changes it to MAX, so the buttons can get back to following.

Out of scope: the Lambda API, dice table requests, colors and shift indexes, the roller, and the summary rows (Range, Mean, Std dev).

2. Data models (models.js)

RollBound

/** @typedef {number | 'MIN' | 'MAX'} RollBound */

Functions

functionreturnsnotes
parseRollBound(text)RollBound | null Trims the text. min/max in any case give 'MIN'/'MAX', and a whole number gives that number. Anything else gives null.
stepRollBound(text, delta, rollLimits)string: the new box text A number becomes number + delta. MIN and MAX step from the roll they stand for: MIN + 1 gives lowest + 1, and MAX − 1 gives highest − 1. Unparseable text, and MIN/MAX while rollLimits is null, come back unchanged. It doesn't snap: MIN − 1 returns lowest − 1, and the render that follows snaps that back to MIN.

StatsRequest

fieldtypenotes
idstringunchanged
lowInput, highInputstring the raw box text. Now defaults to 'MIN' / 'MAX' instead of blank
submittedBounds{low: RollBound, high: RollBound} | null replaces submittedRange. Stored as typed and not sorted, because MIN/MAX are only known at render
shiftIndexnumber | nullunchanged

Methods:

  • submit(shiftIndex) parses both inputs with parseRollBound and sets submittedBounds. The form's pattern ensures only valid text reaches it. Shift assignment is unchanged.
  • resolveRange(rollLimits) returns a sorted RollRange, with MIN replaced by rollLimits.low and MAX by rollLimits.high.
  • snapToRollLimits(rollLimits) applies the snap rule to lowInput, highInput and both submittedBounds. It leaves MIN, MAX, in-range numbers and unparseable text alone.

The SubmittedStatsRequest typedef and isSubmittedStatsRequest switch to submittedBounds. getUnusedShiftIndex in colors.js needs no change.

Derived values (computed in render(), never stored)

  • rollLimits: the lowest and highest rolls of the loaded tables, or null when none are loaded. It's computed as it is today (getLowestAndHighestRolls), behind a small getRollLimits() helper so the step action can use it too.
  • StatsRow.range: each submitted request resolved once with resolveRange(rollLimits). The plot and the stats table read it instead of statsRequest.submittedRange.

3. Views

Markup (index.html)

In statsRequestTemplate, each end becomes a group of a label, a − button, a text box and a + button:

<span class="rollBound">From
    <button type="button" class="iconButton" name="lowDown" aria-label="Step From down">−</button>
    <input type="text" name="low" aria-label="From" list="rollBounds" required
           pattern="[Mm][Ii][Nn]|[Mm][Aa][Xx]|-?[0-9]+" title="MIN, MAX, or a whole number"
           autocomplete="off" spellcheck="false">
    <button type="button" class="iconButton" name="lowUp" aria-label="Step From up">+</button>
</span>
  • The "to" group is the same, with high, highDown and highUp names.
  • It's a <span>, not a <label>. A label wrapping the buttons would label the first button instead of the box, so aria-label names the box.
  • One <datalist id="rollBounds"> with MIN and MAX options is shared by every box. It suggests the two words; it doesn't restrict what can be typed.
  • required and pattern make the browser block a blank or invalid submit, as type="number" blocks a blank one today.

Styles (styles.css)

  • Rename .statsRequest label to .statsRequest .rollBound. Each group is a flex item, so it stays together when the row wraps.
  • The step buttons reuse .iconButton, which is already 44px on phones.
  • .statsRequest input widths are unchanged. The existing input[type=text] rules cover the boxes.

StatsRequestView

  • The constructor finds the four step buttons. Each one calls actions.step(bound, delta), with bound being 'low' or 'high' and delta being ±1.
  • update(model) drops its rollLimits parameter and the min/max attribute code. It still writes the box values only when they differ from the model.

4. Connecting views to models

  • Snapping: in render(), when rollLimits isn't null, call snapToRollLimits(rollLimits) on every stats request before the views update. This replaces fillBlankStatsInputs, which is deleted. Because it runs on every render, the same rule covers a number typed and submitted out of range, a step past either end, and tables changing under a range that was already submitted.
  • Stepping: onPageLoad implements step(bound, delta). It sets lowInput or highInput to stepRollBound(input, delta, getRollLimits()) and calls render(). Stepping changes the box only. Like the spinner today, it doesn't recalculate; Calculate does. Stepping past either end snaps: with a lowest roll of 3, − on 3 gives 2, which the render snaps to MIN. Likewise, + on the highest roll gives MAX.
  • Stats rows: getStatsRows(loaded, rollLimits) returns [] when rollLimits is null. Otherwise it resolves each submitted request and stores the result as StatsRow.range. renderPlot loops over the rows and then their cells, so each cell uses its row's range. renderStatsTable labels the row from range.

8. Decisions and open questions

Decided

  1. Out-of-range pinned numbers snap to MIN/MAX, in both the box and the submitted range. The pin is lost: if the range widens again later, the end stays MIN. Instead we could keep the pin and clamp it quietly, but then the box would show one number while the stats use another.
  2. The boxes hold the word MIN/MAX. We decided against an empty number box with a faded MIN/MAX hint, even though it would keep the spinner and the phone number pad, because the word in the box shows exactly what it does.
  3. − / + buttons replace the spinner. A number box can't display the word MIN, so faking one with a stand-in number and an overlay was ruled out. It would fight the browser, the stand-in number would move whenever the tables change, and screen readers would read the wrong value.
  4. Stepping past the lowest or highest roll gives MIN/MAX. − on the lowest roll becomes MIN, and + on the highest roll becomes MAX. stepRollBound doesn't snap itself; the render after the step does. So no button needs disabling, and there's only one snap rule.
  5. Stepping doesn't recalculate, matching the spinner today. Calculate still does.
  6. The datalist is shared. One rollBounds list serves every box, including boxes for ranges added later.

Open

  1. Datalist behavior differs by browser. Chrome filters suggestions by the current value, so a box holding MIN may offer only MIN until it is cleared, which makes switching straight from MIN to MAX take an extra step. This is acceptable as specced. If it proves annoying, add a way to pick MIN/MAX directly.
  2. Snapping a half-typed value. A render can happen while the user is typing, for example when a dice table fetch finishes. If the half-typed number is out of range at that moment (typing 1 on the way to 15 while the lowest roll is 3), it snaps to MIN. This is rare, and it's accepted as specced.
